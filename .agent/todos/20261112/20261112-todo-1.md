# Phase 0 — Project Setup and Documentation Alignment

## Tasks

### 01 — Review repository state and project-agent conventions

Read the current Project Info, agent instructions, TODO conventions, Game specifications, and Core handoff. Establish the actual repository state and identify stale or conflicting project-level descriptions before changing them.

### 02 — Reorganize Project Info for the game

Update the Project Info structure and content to describe the phrase-guessing game as the project product while retaining the Core as the underlying streaming foundation. Follow the repository's Project Info instructions and the specific scope/decisions recorded in this TODO. Preserve existing Core documentation and avoid rewriting its contracts.

### 03 — Align architecture and source-layout guidance

Define the intended game/Core boundary and initial Rust module organization. Keep game rules independent of YouTube API, OAuth, FFmpeg, and renderer implementation details. Record the agreed structure in the repository's designated architecture/structure documents.

### 04 — Verify documentation consistency

Check links and consistency among the Project Brief, Project Info, docs/Game/, and docs/game-foundation.md. Resolve contradictions introduced by the reorganization and record any intentionally deferred implementation decisions.

### 05 — Add phase-level tests and documentation checks

Verify required Project Info files and cross-references exist, validate Markdown links where tooling permits, and document the resulting project organization and source-of-truth hierarchy.

## Delivery Expectations

- Include phase-appropriate automated tests and any required manual validation in the implementation tasks; do not defer testing to a later phase.
- Update the relevant documentation as part of this phase. Prefer references to the source-of-truth specifications over copying their content into this TODO.
- Resolve any still-open decision needed by a task before implementing that behavior, and record the decision in the appropriate specification.
- Preserve existing Core contracts unless a separately justified and tested change is explicitly required.
- Keep the work locally testable wherever practical. Do not introduce remote deployment or VPS setup work.
