# Phase 0 — Project Setup and Documentation Alignment

## Tasks

### 01 — Review repository state and project-agent conventions

Read the current Project Info, agent instructions, TODO conventions, Game specifications, and Core handoff. Establish the actual repository state and identify stale or conflicting project-level descriptions before changing them. Inspect the current source tree and configuration rather than assuming the target architecture already exists.

### 02 — Define the target Project Info organization

Before editing Project Info, determine the responsibilities and source-of-truth relationships of its files. The resulting organization must make these distinctions explicit:

- The project is now the YouTube chat-controlled phrase guessing game; the reusable YouTube streaming Core is its existing technical foundation.
- `.agent/project-info/brief.md` remains the concise project-level requirements and scope source, with detailed game behavior delegated to `docs/Game/`.
- `.agent/project-info/product.md` describes the game experience, audience, goals, and non-goals rather than describing the standalone streamer as the product.
- `.agent/project-info/context.md` records the actual current implementation status and immediate next work. Do not claim planned game features are already implemented.
- `.agent/project-info/architecture.md` describes the intended game/Core boundaries and target module responsibilities while distinguishing them from the actual current Core structure documented in `docs/game-foundation.md`.
- `.agent/project-info/tech.md` describes the actual Rust/Core stack and the planned Node.js phrase-collection subproject without implying that either planned component already exists.
- Existing Project Info instructions and agent entry points must remain valid and point agents to the correct source-of-truth documents.

All Project Info content and newly authored documentation must remain in English. Avoid copying the detailed game rules into Project Info; link to the relevant Game specification instead.

### 03 — Reorganize and update Project Info

Apply the approved organization from Task 02. Update the required Project Info files and any agent-facing references required by the repository's instructions. Preserve the existing Core documentation and its factual implementation details. Do not rewrite Core contracts to match the planned game architecture.

### 04 — Align architecture and source-layout guidance

Define the intended game/Core boundary and initial Rust module organization. Keep game rules independent of YouTube API, OAuth, FFmpeg, and renderer implementation details. Account for the separate Node.js collector subproject outside `src/`. Record the agreed structure in the repository's designated architecture/structure documents, clearly distinguishing planned paths from existing paths.

### 05 — Verify documentation consistency

Check links and consistency among the Project Brief, Project Info, docs/Game/, and docs/game-foundation.md. Resolve contradictions introduced by the reorganization and record any intentionally deferred implementation decisions. Ensure that Core documentation remains the source of truth for actual Core behavior and docs/Game remains the source of truth for game-specific requirements.

### 06 — Add phase-level tests and documentation checks

Verify required Project Info files and cross-references exist, validate Markdown links where tooling permits, and document the resulting project organization and source-of-truth hierarchy. No game runtime implementation is part of this phase.

## Delivery Expectations

- Include phase-appropriate automated tests and any required manual validation in the implementation tasks; do not defer testing to a later phase.
- Update the relevant documentation as part of this phase. Prefer references to the source-of-truth specifications over copying their content into this TODO.
- Resolve any still-open decision needed by a task before implementing that behavior, and record the decision in the appropriate specification.
- Preserve existing Core contracts unless a separately justified and tested change is explicitly required.
- Keep the work locally testable wherever practical. Do not introduce remote deployment or VPS setup work.
